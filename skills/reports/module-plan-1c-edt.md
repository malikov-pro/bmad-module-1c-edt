# Module Plan

## Vision

**Для** разработчика 1С, ведущего конфигурацию в EDT и применяющего BMAD,
**модуль «1C EDT» (`e1c`)** — прослойка учёта стека внутри BMAD,
которая подмешивает в контур setup / build / review правила работы с 1С: читать и менять конфигурацию **только через EDT-MCP**, считать работу сделанной по **зелёному EDT** (ошибки по затронутым объектам чистые + YAxUnit прошёл).
**В отличие от** готовых наборов 1С-правил (ai_rules_1c, SteelMorgan), модуль не тянет чужие MCP и чужую методологию: он конвертирует применимое под единственный доступный контур исполнения (EDT-MCP), а контракт инструментов берёт живым из самого плагина.

## Architecture

Модель: **прослойка учёта стека** (подтверждено Q5). Без новых агентов, без замены методологии BMAD (Q7). Модуль поставляет четыре элемента:

1. **Правила и практики `e1c-*` (медленный слой).** Конвертированное EDT-совместимое подмножество ai_rules_1c (T1; база сверки `comol/ai_rules_1c@e59525d042c1`) + собственные правила контура: «прочитал MCP → записал MCP → EDT зелёный», гейт ИБ-only-through-EDT, деструктивный gate, YAxUnit в определении «зелёного», билингвальность Name vs Synonym vs тип.
2. **Setup-скилл.** Установка стека в бизнес-проект: проверка доступности сервера EDT-MCP (`get_server_status`); установка пакета `agent/`+`rules/` из репо плагина, пиннованного на тег релиза; запись маркеров в `.dev.env` (`EDT_MCP_RULES_REF`, `IB_UPDATE_CHANNEL=edt-only`, `AI_RULES_SYNC_REF`); маркированный блок стека в корневом `AGENTS.md` (владеет BMAD — блок ведём idempotent-но, merge-safe); стабы для клиентов, не читающих `AGENTS.md`.
3. **Updater-скилл (T2).** Обновление пакета EDT-MCP на новый тег релиза через GitHub API (`releases/latest` → `tag_name`; тело релиза = отчёт об изменениях из PR); обновление маркера; повторный прогон гейта.
4. **Гейт версии.** При активации любого `e1c-*` скилла — сверка `EDT_MCP_RULES_REF` проекта с минимально поддерживаемой версией модуля; расхождение → стоп + сообщение пользователю; пакет отсутствует → установочная инструкция.

### Два темпа контента (Q6)

| Слой | Темп | Где живёт |
|---|---|---|
| Имена/параметры инструментов | каждый релиз плагина | нигде не версонируем: `tools/list`, `get_tool_guide` |
| Правила вызова, безопасность записи | синхронно с релизами | пакет `agent/`+`rules/` плагина, ставится в проект |
| Принципы, гейты, BSL-практики, процесс | медленно | скиллы `e1c-*` |

### Приоритет правил (сверху вниз)

текущий запрос пользователя > проектные правила клиента > гейты модуля (`USER-RULES.md`) > правила `e1c-*` > пакет правил EDT-MCP > внутренняя документация проектов-источников.

### Матрица владения слоями стека

требования/PRD/архитектура — BMAD (L3); спеки задач/стандарты BSL/верификация — конвертированный L1; порядок работ/тестовый контур/ревью — выборочный L2 (SteelMorgan: песочница, кросс-ревью, изоляция тестов); все операции с метаданными/кодом/ИБ — EDT-MCP (L0). Граница L1/L2 уточняется в Фазе 5 (Q3).

### Memory Architecture

Без отдельной памяти модуля в MVP. Состояние живёт в самом проекте: `.dev.env` (маркеры версии/канала), `USER-RULES.md` (гейты), маркированный блок `AGENTS.md`. Это stateless-слой: каждый запуск скилла читает состояние проекта, а не накапливает своё.

### Memory Contract

Не применимо (нет памяти модуля) — фиксируем явно. Пересмотр: после MVP, если появится потребность в обучении на конкретном проекте.

### Cross-Agent Patterns

Новых агентов нет (Q7). Взаимодействие — через общий always-on контекст (блок стека видят все сессии клиента) и через определение done 1С-историй BMAD («зелёный EDT»), которое проверяется в существующем ревью BMAD.

## Setup Extensions

Setup-скилл делает больше записи конфига:

1. Проверка окружения: EDT-MCP отвечает (`get_server_status`), git есть.
2. Установка пакета `agent/`+`rules/` EDT-MCP на пиннованный тег (пути зависят от клиента: `.agents/skills`, `.claude/skills`, …).
3. Запись маркеров `.dev.env` + текста ИБ-gate в `USER-RULES.md` (файл никогда не перезаписывается установщиками — безопасно).
4. Маркированный блок стека в `AGENTS.md` + стабы для клиентов без `AGENTS.md`.
5. Чек-лист «установите YAxUnit в целевую ИБ» (без автодействий).
6. Отчёт о том, что проверять вручную (Eclipse-плагин, публикация ИБ).

## Integration

- **bmm (родитель):** стори BMAD получают 1С-определение done («зелёный EDT»); bmad-build/bmad-review работают под always-on контекстом блока стека. Модуль не добавляет агентов и не меняет фазы BMAD.
- **Родительский стек:** L2-элементы (SteelMorgan: песочница, кросс-ревью вторым агентом, политики изоляции тестов) и будущие MCP-серверы пользователя (syntax-checker, graph/code-metadata, docs, templates) подключаются отдельными задачами вне MVP модуля; их точки входа — маршрутизация в правилах `e1c-*`.

## Ideas Captured

### Искра

- Нужны **правила работы с 1С**, совместимые с BMAD: при работе по методологии должны быть понятны ограничения и подходы платформы 1С (метаданные, EDT, BSL, ИБ, расширения, билингвальность). Это не «вместо BMAD» и не отказ от правил 1С — это 1С-линза внутри BMAD.
- Неверно было сформулировать как «не нужен ещё один набор правил 1С». Нужен именно набор правил 1С, но такой, который стыкуется с BMAD-циклом и с доступным EDT-MCP, а не с чужими MCP.
- Единственный доступный контур исполнения: EDT-MCP (DitriXNew/EDT-MCP). Правила «как не сломать EDT» — в CLAUDE.md репозитория плагина: транзакции BM, синонимы по коду языка, деструктивные операции только по явному запросу, билингвальность Name vs Synonym vs тип.
- Есть сильные источники методологии 1С, но они завязаны на недоступные MCP:
  - SteelMorgan/1c-agent-based-dev-framework — skills, capability registry, 1c-mcp / session-manager, циклы spec/TDD/review.
  - comol/ai_rules_1c — graph/syntax/templates/data/docs MCP, MCP-first поиск фактов о платформе.
- Принцип адаптации: брать процесс и практики (цикл, guardrails, BSL, метаданные, ревью), не копировать tool-id чужих серверов. Если capability нельзя закрыть EDT-MCP — явно сказать «нет доказательства» / «сделай вручную», а не притворяться.

### Кто и зачем

- Пользователь: разработчик 1С, который ведёт конфигурацию в EDT и хочет применять BMAD (PRD → архитектура → stories → build → review) без выдуманных метаданных и без правок XML руками в обход модели EDT.
- Инвариант канала записи (подтверждён пользователем): конфигурацию 1С меняем **только вызовом инструментов EDT-MCP**. Файлы исходников конфигурации (XML выгрузки, `.bsl` на диске, формы в файловой модели) агент не редактирует напрямую — даже если они видны в workspace.
- Ценность: агент знает, *когда* звать EDT-MCP, *чего не трогать*, *как* писать BSL и менять метаданные, *как* проверять результат в EDT — даже если нет 1c-mcp / graph / syntax-checker / infobase MCP.

### Решения сессии (2026-08-24)

- Git: `.gitignore` на `.agents/`, `_bmad/`, `_bmad-output/` — это среда разработки модуля, не исходники.
- Маршрут: Ideate через bmad-module-builder, не спека через bmad-build.
- Главная работа модуля (все ок): реализовывать фичи через EDT-MCP; ревью BSL/метаданных; создавать/менять объекты метаданных; тесты (YAxUnit и аналоги); весь цикл BMAD с 1С-ограничениями.
- Первый срез (MVP): EDT-playbook + практики BSL/метаданных, которые живут без чужих MCP, плюс setup для установки в 1С-проект.
- Клиенты: Cursor в приоритете; остальные клиенты, которые умеет install BMAD — следующим срезом, не блокером MVP.
- **Ядро ценности (зафиксировано):** один контур `прочитал MCP → записал MCP → EDT зелёный`. Три слоя не выбираются по отдельности — это одно определение «сделано» для 1С в BMAD.
- **Когда контур обязателен (зафиксировано):** при **реализации фичи** контур обязателен целиком (прочитал → записал → EDT зелёный). Перед планированием контур **полезен** как разведка текущего состояния (только чтение MCP) — не блокер PRD/архитектуры, но факты о конфигурации лучше брать из EDT, а не из памяти.
- **Правила 1С в MVP (зафиксировано, все must-have):** (1) BSL — запросы, транзакции, привилегированный режим, клиент/сервер; (2) метаданные и управляемые формы, не ломать состав формы; (3) расширение vs основная конфигурация; (4) не выдумывать БСП/типовые подсистемы; (5) тесты YAxUnit как часть «зелёного»; (6) деструктивное (rename/delete, обновление ИБ) — только по явной просьбе.
- **YAxUnit (уточнено):** EDT-MCP умеет запускать тесты (`run_yaxunit_tests`), если в ИБ установлено расширение [YAxUnit](https://github.com/bia-technologies/yaxunit). Без расширения tool падает (нет JUnit XML) — не притворяться, что тесты прошли. Setup модуля: проверить/требовать расширение в базе.
- **Идентичность (зафиксирована):** имя «1C EDT», код `e1c`, expansion поверх BMad Method (`bmm`). Все skills будут `e1c-*`. Описание: правила работы с 1С в BMAD через EDT-MCP: читать и менять конфигурацию только через MCP, считать работу сделанной по зелёному EDT.

### Зазоры, которые модуль должен закрыть

- BMAD «из коробки» не знает EDT, транзакций BM, FQN метаданных, форм, обновления ИБ.
- SteelMorgan/comol учат агента звать MCP, которых нет → агент либо галлюцинирует структуру, либо лезет в файлы выгрузки.
- Нужен «переводчик capability → EDT-MCP»: list/read/write metadata, module source, errors, compile, form layout — и честный отказ там, где EDT-MCP не даёт (живой запрос к ИБ, граф влияния, официальная документация платформы как MCP).

### Сырые идеи (ещё не архитектура)

- Playbook «как ходить в EDT»: сначала прочитать проект/конфигурацию, потом объект, потом модуль; запись только в write-boundary; после записи — ошибки проекта / компиляция.
- Адаптация bmad-build: 1С-история не считается done, пока EDT не подтвердил (маркеры, компиляция), а не только diff в git.
- Практики BSL, которые не требуют чужого MCP: именование, слои, запросы, привилегированный режим, транзакции, формы — как правила; проверка — через EDT errors + чтение модуля, не через syntax-checker MCP.
- Деструктивное: rename/delete metadata, update_database, delete_project — отдельный жёсткий gate.
- Билингвальность: тип можно по-русски/по-английски; Name объекта — как в конфигурации; синоним не использовать как ключ.
- Расширение поверх BMad Method (bmm), а не замена: PRD/архитектура/stories остаются; этот модуль добавляет 1С-линзу на реализацию и ревью.
- MVP не тащит отдельных агентов «аналитик 1С» / «архитектор 1С» как замену PM/архитектору BMAD. Открыта развилка: агент-персона 1С vs только правила внутри bmad-build/review vs гибрид.
- **Слой стека, не вторая методология (идея пользователя, ещё не архитектура):** модуль — прослойка, которая подмешивает в BMAD учёт технологического стека «1С + EDT + EDT-MCP», так же как BMAD уже учитывает стек через архитектуру и `AGENTS.md` / project-context. Методология (PRD → stories → build → review) остаётся BMAD. Правила вызова EDT-MCP **будут меняться вместе с инструментом** — не копировать CLAUDE.md навсегда, а подтягивать актуальный контракт (tools/list, tool guides). Практики 1С (BSL, формы, расширение, YAxUnit, деструктивное) живут дольше, чем имена tool.
- Setup: проверить, что EDT-MCP виден агенту; подсказать, если tools/list пуст; не устанавливать EDT-MCP за пользователя (это Eclipse-плагин).
- Позже: адаптеры под Claude Code и другие install-цели BMAD — те же skills, другой layout установки.

### Ядро ценности (зафиксировано)

Один контур, не три фичи:

**прочитал MCP → записал MCP → EDT зелёный**

- Читать факты о конфигурации только из EDT-MCP (не выдумывать метаданные, не считать синоним именем).
- Писать только через EDT-MCP (файлы исходников конфигурации не редактировать).
- Считать работу done только когда ошибки EDT по затронутым объектам чистые (git-diff недостаточен).

Правила 1С в модуле описывают ограничения и подходы на каждом шаге этого контура и стыкуются с BMAD-циклом (PRD → архитектура → story → build → review).

**Два режима контура (зафиксировано):**

- **Реализация фичи — обязательно.** Нельзя писать в конфигурацию и закрывать story без полного контура.
- **Перед планированием — полезно.** Разведка текущего состояния через чтение MCP (какие объекты/реквизиты/формы есть). Не запрещает планировать новые объекты; запрещает выдавать догадку за факт о существующей конфигурации.

**Правила 1С в первом срезе (зафиксировано — все must-have, не backlog):**

1. BSL: запросы, транзакции, привилегированный режим, клиент/сервер.
2. Метаданные и управляемые формы: не ломать состав формы.
3. Расширение vs основная конфигурация.
4. Не выдумывать БСП / типовые подсистемы — только то, что подтвердил MCP или пользователь явно указал.
5. Тесты (YAxUnit) входят в определение «зелёного», не отдельный nice-to-have.
6. Деструктивное: rename/delete метаданных, обновление ИБ — только по явной просьбе.

**YAxUnit (уточнено пользователем, зазор закрыт):** EDT-MCP запускает тесты через `run_yaxunit_tests` (отчёт JUnit Markdown), если в целевую ИБ добавлено расширение [YAxUnit](https://github.com/bia-technologies/yaxunit). Без расширения — ошибка, нет XML. «Зелёный» = ошибки EDT чистые + `run_yaxunit_tests` прошёл. Если расширения нет — не врать про зелёные тесты, сказать поставить YAxUnit в базу.

### Слой стека (идея пользователя, Phase 2)

Модуль не заменяет BMAD и не обязан быть «ещё одним фреймворком 1С». Он — **прослойка учёта стека**, по аналогии с тем, как BMAD уже читает архитектуру и `AGENTS.md`: «в этом репо стек такой, работай так».

Здесь стек = конфигурация 1С в EDT, канал = EDT-MCP.

Два темпа изменений:

- **Контракт EDT-MCP (быстрый):** имена tool, параметры, транзакции, новые операции. Источник правды — живой MCP (`tools/list`, `get_tool_guide`), плюс обновляемый тонкий playbook в модуле, а не форк CLAUDE.md.
- **Практики 1С (медленный):** BSL, формы, расширение vs основная, БСП не выдумывать, YAxUnit, деструктивный gate. Это стабильные правила модуля.

Следствие для агент vs playbook: прослойка по умолчанию **подмешивается** в bmad-build / review / (опционально) разведку, когда стек 1С+EDT. Отдельная персона — надстройка, не обязательное ядро слоя.

### Вопросы, которые ещё не закрыты (Phase 2)

- Подтвердить модель «прослойка стека» как архитектуру MVP.
- Живой контракт MCP vs версионируемый playbook в модуле — что обновляем мы, что всегда берём с сервера.
- Агент-персона в MVP или только слой + setup, который пишет стек в project-context / AGENTS.md.
- Список правил MVP закрыт или ещё роли/RLS/обмен/регламентные.
