# e1c-testing-yaxunit — тесты как часть «зелёного»

Требует `e1c-core` («зелёный» = ошибки EDT чистые **и** тесты прошли) и `e1c-bsl-practices` (стиль кода тестов тот же). Конвертировано из пакета EDT-MCP (`agent/skills/edt-mcp-project-yaxunit`) и практик SteelMorgan (`yaxunit-isolation`, `test-zero-residue`); база сверки апстрима — `AI_RULES_SYNC_REF` в `.dev.env` проекта.

## 1. Предусловие: расширение YAxUnit в целевой ИБ

`run_yaxunit_tests` работает, только если в целевую информационную базу установлено расширение [YAxUnit](https://github.com/bia-technologies/yaxunit). Без него инструмент падает (нет отчёта JUnit). В этом случае — **честный отказ**: сообщи пользователю, что нужно поставить расширение, не имитируй зелёные тесты и не считай задачу сделанной. Наличие проверяй по данным цели (`list_configurations`, `get_applications`) и актуальному гайду инструмента — не пробным прогоном: неудачный запуск ничего не доказывает. Установка расширения — ответственность пользователя/команды.

## 2. Запуск: границы задачи и селекторы

Граница задачи: этот скилл — про YAxUnit-тесты. Он не про универсальные UI/E2E-тесты; прогон никогда не наводится на неопознанную, общую или **боевую** информационную базу — только на выделенную тестовую.

- Цель разрешай точно: конфигурация запуска (`list_configurations`) или проект+приложение (`get_applications`); креды — `set_infobase_credentials`, только когда это необходимо и авторизовано.
- Селектор фиксирован до запуска, имена методов не угадываются:
  - целый модуль: `modules=ИмяМодуля`, без `tests`;
  - отдельный тест: `tests=ИмяМодуля.ИмяМетода` — ровно в этой форме;
  - никогда не передавай в `tests` только имя модуля или только имя метода;
  - `extensions` и `tags` — только по документированным семействам фильтров, никаких выдуманных масок.
- После невалидного селектора, нуля выполненных тестов или отсутствия отчёта — **не повторяй ту же команду**: сверись с актуальным гайдом инструмента и реальной регистрацией тестов, исправь селектор, один чистый прогон.
- В отчёте о прогоне фиксируй фактически отправленные фильтры.
- `updateBeforeLaunch=true` требует явного `updateScope`: `configuration` или точный `extension:<Проект>`; `all` — только когда все зависимые расширения намеренно включены и на это есть право пользователя. Это обновление выполняется внутри санкционированного EDT-канала (ИБ-gate ядра) и отдельного вызова `update_database` не требует; эффект обновления фиксируется в отчёте.
- Долгий прогон — фоновая задача: сохрани `jobId`, опрашивай именно его через `get_job_status`; повторный запуск ради проверки статуса запрещён.

## 3. Интерпретация результата

- Прогон засчитан, только если выполнился хотя бы один задуманный тест. **Ноль выполненных = неопределённый результат**, а не успех — даже если отчёт «зелёный». Исключение: пустой селектор запрошен явно — легитимный результат, фиксируй его как таковой.
- Отчёт JUnit/Markdown читай целиком: упавшие ассерты, ошибки выполнения, пропущенные.
- Задача закрывается только по совокупности ядра: ошибки EDT чистые по затронутым объектам **и** тесты прошли.

## 3а. Отладка и отмена

- Отладка падающего теста: `set_breakpoint` на подозрительную строку → запуск `run_yaxunit_tests` в режиме отладки → `wait_for_break` → ограниченный осмотр кадра → `resume` / `remove_breakpoint`. После прогона — `debug_status`: убедись, что не осталось живых запусков.
- Никогда не возобновляй (`resume`) чужое или неоднозначно принадлежащее приостановленное выполнение.
- Отмена долгого прогона — `cancel_job`, с preview/подтверждением и контролем терминального состояния.
- Истёк согласованный дедлайн, задача ещё живёт? Не бросай владение: продолжай сверку статуса, отменяй только с авторизацией, либо явно передавай пользователю `jobId` и обязательства по очистке точек останова/запусков. Известный незавершённый job сам по себе — небезопасное условие остановки задачи.

## 4. Изоляция: `.ВТранзакции()` по умолчанию

Серверный тест, пишущий в БД, обязан откатывать свои изменения — иначе прогоны оставляют мусор, тесты перестают быть идемпотентными, база деградирует. Механизм YAxUnit: `.ВТранзакции()` открывает транзакцию перед тестом и откатывает после.

MUST:

| Требование | Правило |
|---|---|
| `.ВТранзакции()` сразу после `ДобавитьТестовыйНабор()` | для любого набора серверных тестов с записью в БД |
| Справочники — через `ЮТест.Данные()` | `СоздатьЭлемент(...)` / `КонструкторОбъекта(...).Записать()` — трекаются автоудалением; при сомнении в версии YAxUnit дублируй включением в коллектор (§5) |
| Исключение → обоснование + teardown | набор без `.ВТранзакции()` обязан иметь комментарий-причину перед регистрацией и очистку через `.После("ИмяПроцедуры")` |
| Документы мимо трекинга | созданные `Документы.X.СоздатьДокумент()` не удаляются автоочисткой — явный teardown |
| Перепроведение — свежий объект | перед каждым перепроведением — `Ссылка.ПолучитьОбъект()` заново (моделирует поведение формы), не переиспользуй старый экземпляр |
| Клиентские тесты | `ДобавитьКлиентскийТест` выполняется вне транзакции — откат недоступен, только teardown |

Допустимые исключения из `.ВТранзакции()`:

- **(а) Негативные тесты проведения** (ожидаемый `Отказ`): ошибка внутри вложенной транзакции записи «отравляет» внешнюю («В данной транзакции уже происходили ошибки!»). Решение: без транзакции, данные через `ЮТест.Данные()` + `.УдалениеТестовыхДанных()` + teardown документа в `.После()`.
- **(б) Прод-код с гвардом `ТранзакцияАктивна()`** (двухфазные фиксации, реальные внешние вызовы): запуск в транзакции ломает сам прод-код. Решение: без транзакции, teardown вручную.
- **(в) Клиентские тесты** (`ДобавитьКлиентскийТест`) исполняются вне транзакции — откат недоступен. Тестовые данные для них создаётся серверными обработчиками `Перед`/`После` набора.

Ограничение платформы 8.3.27+: программное перепроведение может дать `[ОшибкаХранимыхДанных]`, которую не лечат ни перечитывание объекта, ни `.ВТранзакции()`. Фолбэк: проверить поведение сценарным слоем (Vanessa/UI), юнит-тест пометить `ЮТест.Пропустить()` с обоснованием в комментарии.

## 5. Zero-residue: тесты не оставляют следов

Инвариант: дельта количества по каждому затронутому справочнику/регистру/документу/**набору записей** до и после прогона = **0**. Ревью блокирует тест, оставивший данные, даже если он «зелёный».

| Правило | Содержание |
|---|---|
| Механизм изоляции обязателен | `.ВТранзакции()` или явный teardown `.После()` при допустимом исключении (§4) |
| Объекты трекаемы | создание данных через `ЮТест.Данные()`, не `Справочники.X.СоздатьЭлемент()` мимо трекинга |
| Нетрекаемое удаляется физически | `ОбменДанными.Загрузка = Истина` + `Удалить()`, порядок: зависимые → владелец; пометка удаления не считается |
| Коллектор обязателен | каждый созданный объект регистрируется в коллекторе в момент создания; teardown проходит по коллектору и работает даже если Act/Assert упали |
| Ошибки удаления не глотаются | сбой `Удалить()` на конфликте версии → повтор со свежим `ПолучитьОбъект()` (ограниченно); не-конфликт или исчерпание — запись уровня `Ошибка` в журнал и продолжение дренажа остальных объектов |
| Сквозной сценарий | если данные обязаны жить во время прогона — явный завершающий шаг зачистки по коллектору |
| Запрет band-aid | скрытие созданного от выборок (спец-флаг, префикс-фильтр) зачисткой не считается — физическое удаление |
| Запрет хрупких селекторов | перебор базы по имени/префиксу (`ПОДОБНО "Тест%"`) — не штатный teardown (риск снести боевые данные); допустим лишь разовой уборкой исторического мусора |

Приёмка включает проверку дельты ключевых объектов до/после как часть критерия фазы — ненулевая дельта = тест не принят (GUARD).

## 6. Связь со сторями BMAD

- AC стори формулируются проверяемо; тесты YAxUnit покрывают поведенческие AC и входят в критерий done.
- Новая функциональность → тесты пишутся вместе с кодом по порядку пайплайна стека (спека → тесты → код → прогон), а не «потом».
- Ревью тестов — по §4–§5 этого файла; ревью остального кода — доменный ревью-скилл модуля `e1c-review`.

## Верификация

Запуск — по §2; результат — §3. Падение теста: сначала прочти отчёт и код теста (`read_method_source`), затем код прод-модуля; исправление — обычным контуром ядра (запись MCP → revalidate → прогон).
