# e1c-updater — актуализация пакета правил и базы сверки

Требует `e1c-core`: задача начинается со штатного активационного гейта ядра (его проверенный тег идёт в отчёт), честный отказ без сети действует и здесь.

Две независимые операции:

1. **Обновление пакета EDT-MCP** (`agent/`+`rules/`) на новый тег релиза.
2. **Сверка апстрима ai_rules_1c** — подготовка отчёта для задачи конвертации в репозитории модуля (бизнес-проект при этом не меняется).

Процедуры установки этот скилл **не дублирует**: он ссылается на шаги `e1c-setup`.

## Предусловия

- Маркер `EDT_MCP_RULES_REF` читается **и** файлы пакета на месте → продолжай.
- Маркера нет, файлы повреждены или версии в клиентских путях расходятся → это режим repair скилла `e1c-setup`, не updater: сообщи и предложи его.
- Определи клиентские каталоги так же, как Шаг 0.4 `e1c-setup` (`.agents/skills/`, `.claude/skills/`, `.cursor/`; нет ни одного — создать `.agents/skills/`).

## 1. Обновление пакета EDT-MCP

### 1.1 Определи текущее и целевое

- Текущее: строка `EDT_MCP_RULES_REF` из `.dev.env`.
- Целевое — по приоритету (как в `e1c-setup`, Шаг 1.1): тег, названный пользователем → значение конфигурации модуля, если задано → `GET https://api.github.com/repos/DitriXNew/EDT-MCP/releases/latest` → `tag_name`; при недоступности API (git работает) — `git ls-remote --tags` + сортировка версий. Сеть недоступна целиком → ручная установка по разделу «Ручная установка (без git)» скилла `e1c-setup`. Несуществующий тег → стоп с перечнем доступных последних тегов.

Сравнение тегов — по семантике ядра: префикс `v` опционален, формат `X.Y.Z`, недостающие сегменты = 0; неразбираемый тег считается расхождением.

### 1.2 Реши

| Ситуация | Действие |
|---|---|
| Целевой = текущему | «Обновление не требуется»; предложи сверку апстрима (§2) |
| Целевой новее текущего | Продолжай |
| Целевой старше текущего | Даунгрейд — только по явному подтверждению пользователя |
| Целевой новее протестированного ядра (`MIN_EDT_MCP_RULES_REF`) | Предупреди заранее: модуль писался под более старый тег; после обновления повторный гейт запросит подтверждение — пользователь должен понимать это до установки |

### 1.3 Отчёт об изменениях — ДО замены файлов

Получи тело релиза целевого тега (`GET /repos/DitriXNew/EDT-MCP/releases/tags/<тег>` → `body`, список PR «What's Changed»). Фолбэки: тело пустое или API недоступен → `git log --oneline <старый-тег>..<целевой-тег>` во временном клоне (появится на шаге ниже). Покажи пользователю изменения **до** того, как что-либо заменено, — это окно принять решение (в том числе отказаться).

### 1.4 Установи

Выполни пункты 3–8 Шага 1 скилла `e1c-setup` (клон пиннованного тега → проверка лейаута → замена управляемых путей с удалением устаревших `edt-mcp-project-*` → копирование `rules/<lang>/` → уборка → проверка результата). Откат после замены: старый пакет удалён — возврат выполняется повторным запуском этого workflow на предыдущий тег (он известен из исходного маркера).

### 1.5 Зафиксируй

Обнови в `.dev.env` **только ключ** `EDT_MCP_RULES_REF=<новый тег>`: файл не перегенерируй, остальные строки (включая чужие) не читай и не выводи.

### 1.6 Повторный гейт и финал

Прогони активационный гейт `e1c-core` заново (маркер ↔ файлы ↔ доступность сервера). Гейт не прошёл → сообщи состояние и варианты (откат на предыдущий тег / починка через `e1c-setup`), задачу не закрывай. Прошёл → напомни о перезапуске клиента (схемы инструментов приезжают в новую сессию).

## 2. Сверка апстрима ai_rules_1c

Подготовка отчёта для задачи конвертации в **репозитории модуля**; бизнес-проект не меняется, ref двигает не updater.

1. Прочитай `AI_RULES_SYNC_REF`. Ключа нет → предложи зафиксировать базу: текущий `main` апстрима (после первой сверки) — и продолжай от него; правки `.dev.env` — только этим одним ключом.
2. Получи коммиты с базы: клон во временный каталог (`git clone --filter=blob:none https://github.com/comol/ai_rules_1c.git <tmp>`) → `git log --oneline <ref>..<default-branch>`; либо GitHub API `/repos/comol/ai_rules_1c/commits?since=<дата>`, переведя SHA в дату через `/commits/<sha>` (`commit.committer.date`). Пустой результат лога проверь на здравость: `git merge-base --is-ancestor <ref> HEAD` — если база не предок (rebase/force-push апстрима), предупреди и пересчитай от ближайшего общего предка.
3. Сгруппируй коммиты — **предварительно**, сверяя затронутые файлы апстрима с инвентарём конвертации в репозитории модуля (заголовки `skills/e1c-*/SKILL.md` с атрибуцией + план модуля):
   - **Кандидаты на конвертацию** — правки правил, чьи темы конвертированы в `e1c-*`;
   - **Не применимо** — завязки на MCP-серверы comol, Designer-ориентированные инструменты, поддержка клиентов;
   - **Требует изучения** — спорные.
   Каждый пункт — с хэшем и ссылкой на коммит.
4. Итог: markdown-список кандидатов (сохранить в файл рядом с задачей конвертации, если пользователь просит). Сама конвертация и поднятие базового ref'а — отдельная задача в репозитории модуля; после неё пользователь/агент актуализирует `AI_RULES_SYNC_REF`. Updater модуль не редактирует и ref не двигает.

## Отчёт

Сводка: было → стало (оба тега), изменения из тела релиза/лога (до замены — как основание решения), какие файлы заменены/удалены, результат повторного гейта (или его отказ и варианты), напоминание о перезапуске клиента; для §2 — группы коммитов с хэшами и ссылками. Финальная строка — всегда по контракту ядра: `EDT tooling: <инструменты> (rules ref <итоговый тег>)`.
