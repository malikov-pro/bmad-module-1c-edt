# e1c-bsl-practices — практики BSL

Требует `e1c-core` (контур «прочитал → записал → зелёный», верификация EDT-native). Содержимое конвертировано из подмножества [ai_rules_1c](https://github.com/comol/ai_rules_1c) (`comol/ai_rules_1c@e59525d042c1`) с адаптацией к контуру EDT-MCP. Часть норм апстрима живёт в их MCP-коллекции `1c-standards` и подключится позже вместе с отдельными аналитическими MCP-серверами; до тех пор здесь действует дистиллированное правило, а не полный канон. Пункты, где этот файл сознательно строже или уже апстрима, помечены `[дельта]`.

## 1. Структура модуля и регионы

Имена регионов — русские, БСП-стилем. Английские (`Public`/`Internal`/`Private`) — нельзя, кроме конфигураций, целиком ведущихся в английской локали **и с регионами, единообразными по всей кодовой базе**. Регионы внутри процедур и псевдорегионы комментариями — запрещены. Регионы не переименовывают, не удаляют и не меняют порядок; пустой обязательный регион остаётся пустым. Семантика: `ПрограммныйИнтерфейс` — публичные экспортные методы (для других модулей конфигурации); `СлужебныйПрограммныйИнтерфейс` — экспорт только для собственных модулей проекта; `СлужебныеПроцедурыИФункции` — внутренние помощники, никогда без `Экспорт`.

Общий модуль:

```bsl
#Область ПрограммныйИнтерфейс
#КонецОбласти

#Область СлужебныйПрограммныйИнтерфейс
#КонецОбласти

#Область СлужебныеПроцедурыИФункции
#КонецОбласти
```

Модуль объекта/менеджера — `ПрограммныйИнтерфейс` → `ОбработчикиСобытий` → `СлужебныеПроцедурыИФункции` (в этом порядке), всё внутри препроцессорной обвязки:

```bsl
#Если Сервер Или ТолстыйКлиентОбычноеПриложение Или ВнешнееСоединение Тогда
// ...
#КонецЕсли
```

Модуль формы — обязательные регионы (в т.ч. пустые): `ОбработчикиСобытийФормы`, по одному `ОбработчикиСобытийЭлементовТаблицыФормы<ИмяТаблицы>` на каждую таблицу формы, плюс `ПрограммныйИнтерфейс` и `СлужебныеПроцедурыИФункции`. Детали состава форм — домен `e1c-metadata-forms` (доменный скилл модуля).

## 2. Запрещённые конструкции

- Тернарный оператор `?(...)`.
- `Выполнить()`, `Вычислить()` — исполнение кода строкой.
- Учётные данные и секреты в коде.
- `Сообщить()` в прикладном коде (пользовательские сообщения — через механизмы БСП/UI конкретного проекта); `ЗаписьЖурналаРегистрации()` без явного основания задачи.
- `Попытка…Исключение` вокруг записи/чтения БД «на всякий случай» — глушит критичные ошибки; исключение либо обрабатывается осмысленно, либо пробрасывается дальше.
- Сравнение булевых с `Истина`/`Ложь`, Yoda-условия (`Если 5 = КоличествоТоваров`).
- `COMОбъект` — кроссплатформенность; если задача кажется без него нерешаемой — это повод проверить платформенный механизм, а не брать COM.

## 3. Именование и типографика

- Самодокументируемые имена; венгерская нотация, имена из глобального контекста 1С, магические числа, отрицательные булевы имена (`ФлагНеНайден`) — запрещены.
- Переменные и процедуры — по назначению, без транслитерации; буква «ё» в идентификаторах не используется.
- Экспортные процедуры/функции документируются (назначение, параметры); нетривиальная логика — короткий комментарий-мотивация.

## 4. Комментарии

Самодокументируемый код предпочтительнее комментариев. Комментарий уместен: мотивация решения, нетривиальный алгоритм, ограничения/побочные эффекты, обход платформенного ограничения (с объяснением, что и почему), маркер техдолга (`TODO No.<задача>: …`). Запрещены: пересказ кода, авторские баннеры и история изменений (это работа git).

## 5. Сначала — переиспользование

Перед новым кодом: поиск существующего экспортного метода в общих/менеджерских модулях проекта (`search_in_code`, `get_module_structure`). Нашёл подходящий — используй как основу, адаптируй только необходимое; переписывание с нуля эквивалентного решения — дефект. То же для платформы: специализированная задача (криптография, регулярные выражения, очереди, полнотекстовый поиск…) начинается с проверки готового механизма платформы через доступные источники (`e1c-core → Не выдумывать БСП и типовые подсистемы`).

## 5а. Доступ к данным и производительность

- Не читай реквизиты ссылок через точку в циклах (`Контрагент.ИНН`) — это скрытый запрос на каждое обращение. Массовое чтение — одним запросом; в проектах с БСП — пакетные функции вида `ЗначенияРеквизитовОбъекта` (наличие подтвердить инструментом, см. `e1c-core → Не выдумывать БСП и типовые подсистемы`).
- Тяжёлая обработка данных — на сервере, пакетами; клиент не должен гонять пообъектные обращения к серверу в цикле.
- Кэшируй неизменяемые значения там, где это оправдано (сеансовые/повторно используемые значения кэша), но не превращай кэш в рассинхронизируемое состояние.

## 6. Запросы

Pre-flight каждого нетривиального запроса:

1. **Метаданные подтверждены** до первого `ВЫБРАТЬ` — таблицы, реквизиты, виртуальные таблицы через инструменты EDT-MCP (`get_metadata_properties`, `find_references`), не по памяти.
2. **Найди проверенную форму** до изобретения скелета — похожий запрос в коде проекта (`search_in_code`); нашёл подходящий — бери за основу (см. §5).
3. **Правильный источник данных** — справочник/документ/срез регистра/виртуальная таблица остатков-оборотов. Неверный источник — дефект проектирования, а не настройка.
4. **Жёсткие запреты:** запросы в циклах; склейка текста запроса со строковыми значениями — только параметры (`ГДЕ Код = &Код`); пропуск `КАК` для псевдонимов; фильтрация виртуальных таблиц через `ГДЕ` вместо параметров виртуальной таблицы; потеря результата `Запрос.Выполнить()` без переменной; ограничение выборки без `ПЕРВЫЕ N`, когда нужен именно поднабор; лишний `РАЗЛИЧНЫЕ` внутри операндов `ОБЪЕДИНИТЬ` или поверх `СГРУППИРОВАТЬ ПО`.
5. **Временные таблицы:** каждая временная таблица, участвующая в `СОЕДИНЕНИЕ`/`ОБЪЕДИНИТЬ`/`В (ВЫБРАТЬ…)`, индексируется по ключам соединения (`ИНДЕКСИРОВАТЬ ПО`, 2–3 избирательных поля); коррелированные подзапросы заменяются временной таблицей + соединением; периодичность виртуальной таблицы согласована с ключами соединения.
6. **Проверка текста:** `validate_query` (EDT-MCP) до помещения запроса в модуль — синтаксис и семантика против метаданных проекта, без обращения к ИБ.

## 7. Транзакции и блокировки

Принципы (полный канон придёт позже вместе с отдельными аналитическими MCP-серверами):

- Пара обязательна: `НачатьТранзакцию` завершается либо `ЗафиксироватьТранзакцию`, либо `ОтменитьТранзакцию`; после ошибки транзакцию надо явно откатить — попытки писать дальше в отменённой транзакции недопустимы. Контекст «в транзакции или нет» проверяй `ТранзакцияАктивна()`.
- Проверь, не открыт ли уже внешний контур транзакции (например, транзакция записи объекта) — вложенные `НачатьТранзакцию` без нужды не открывать.
- Внутри транзакции: никаких диалогов, внешних вызовов, длительных вычислений — держим её короткой.
- Управляемые блокировки перед чтением «для контроля остатков»: режим блокировки и порядок захвата согласованы между участниками операции — разнобой порядка = дедлоки.
- Ошибка внутри транзакции → откат и проброс осмысленного сообщения; молчаливое проглатывание запрещено.

### Журналирование

Ошибки и значимые события пишутся в журнал регистрации: уровень по тяжести (`Ошибка`/`Предупреждение`/`Информация`), осмысленное имя категории, сообщение пригодно для диагностики (что упало, с какими данными). Секреты и персональные данные в журнале запрещены. Полная стратегия логирования — кандидат на конвертацию из апстрима позже.

## 8. Клиент/сервер и асинхронность

- Директивы компиляции честные: серверная логика — `&НаСервере`/серверные общие модули; клиент не ходит на сервер в цикле — выноси пакетную обработку на сервер целиком.
- Асинхронность 8.3.18+ (`Асинх`/`Ждать`): каждый `Асинх`-вызов сопровождается `Ждать` там, где нужен результат или перехват ошибки — **без `Ждать` исключения теряются молча**; `Асинх`-обработчик события формы не блокирует форму — последовательность «вызвал и забыл» может выполнить код после закрытия формы.

## 9. Привилегированный режим

`УстановитьПривилегированныйРежим(Истина)` — только в серверных служебных модулях, узко и обоснованно (операции, требующие обхода RLS по задаче); включение «чтобы работало» — дефект безопасности. После участка — выключение обратно.

## 10. Расширения (CFE)

- Типы перехватчиков: `&Перед` / `&После` — дополнение; `&Вместо` — полное замещение (крайняя мера); `&ИзменениеИКонтроль` — контролируемая правка заимствованного тела.
- `ПродолжитьВызов()`: в `&Перед` — вызывать, если логика должна продолжиться; в `&После` — не вызывать (уже выполнилось); в `&Вместо` — вызываешь сам, когда нужен исходный алгоритм. Потерянный `ПродолжитьВызов` в `&Перед`/`&Вместо` ломает типовое поведение.
- Собственные процедуры расширения именуются с префиксом-алиасом расширения (`Расш1_`, `МоеРасш_`), алиас без буквы «ё».
- Изменения типового кода помечаются маркерами начала/конца изменения — так их видно при обновлении конфигурации.
- Расширение vs доработка основной конфигурации: для типовых конфигураций на поддержке — расширение первым (`adopt_metadata_object` в EDT-MCP; см. `e1c-metadata-forms`).

## Верификация (EDT-native)

После записи кода — по методике ядра:

1. `revalidate_objects` по изменённым объектам → дождаться завершения.
2. `get_project_errors` с фильтром по проекту/серьёзности; маркеры сопоставлены затронутым файлам.
3. Для запросов — `validate_query` текста каждого нового/изменённого запроса.
4. **Самопроверка после правки**, масштабированная к объёму изменения: корректность и граничные случаи изменённого фрагмента; рядом с транзакционными путями — блокировки/транзакции; для полного цикла дополнительно безопасность и параллелизм. Блокирующий дефект валидации требует чистого подтверждающего прогона на изменённом состоянии.
5. Чего здесь **нет**: сторонние syntax-checker/review MCP (подключаются отдельной задачей). До того — эта цепочка является полной.
