# e1c-setup — установка и починка стека в проекте

Workflow выполняется агентом по шагам. Перед началом загрузи ядро `e1c-core`: его константы (`MIN_EDT_MCP_RULES_REF`, переопределяемая конфигом модуля `edt_mcp_min_version`) и гейты действуют и здесь.

Устанавливается: пакет правил EDT-MCP `agent/`+`rules/` (пиннится на тег релиза), маркеры `.dev.env`, текст ИБ-gate в `USER-RULES.md`, маркированный блок стека в `AGENTS.md`.

Не устанавливается (только проверяем/подсказываем): Eclipse-плагин EDT-MCP, расширение YAxUnit в целевой ИБ.

Запуск с аргументом `configure` — только Шаг R (переконфигурация модуля в `_bmad`, без переустановки стека). Полный запуск без аргументов = Шаг R → Шаги 0–5.

## Шаг R. Регистрация модуля в BMad

Модуль регистрируется в `_bmad` проекта: конфиг и справка возможностей. Если `{project-root}/_bmad/config.yaml` не существует — BMad Method не установлен: сообщи пользователю и предложи `npx bmad-method install`, затем повтори шаг.

1. Прочитай `./assets/module.yaml` (метаданные + переменные) и `./assets/module-help.csv`.
2. Если секция `e1c` уже есть в `_bmad/config.yaml` — это обновление: сообщи.
3. Собери ответы на переменные модуля (покажи значения по умолчанию в скобках, дай ответить один раз только изменениями): `edt_mcp_min_version` (default `v2.15.1`), `rules_lang` (default `ru`). Аргументы запуска маппятся на ключи, остальное — defaults.
4. Запиши временный JSON вида `{"module": {"edt_mcp_min_version": "...", "rules_lang": "..."}}` (значения с литеральным токеном `{project-root}` не подставлять путями!) и выполни:

```bash
uv run ./scripts/merge-config.py --config-path "{project-root}/_bmad/config.yaml" --user-config-path "{project-root}/_bmad/config.user.yaml" --module-yaml ./assets/module.yaml --answers <temp.json> --legacy-dir "{project-root}/_bmad"
uv run ./scripts/merge-help-csv.py --target "{project-root}/_bmad/module-help.csv" --source ./assets/module-help.csv --legacy-dir "{project-root}/_bmad" --module-code e1c
```

Пути-аргументы — реальные пути (токен `{project-root}` разрешить), иначе скрипты упадут с ошибкой. Ненулевой код возврата — покажи ошибку и остановись.

5. Покажи из JSON-вывода скриптов: записанные ключи, fresh install vs update. Поздравление пользователю — `module_greeting` из module.yaml.

После регистрации продолжай к Шагу 0 (полный запуск) или заверши (аргумент `configure`).

## Шаг 0. Режим и окружение

1. **Определи режим.** В корне проекта проверь `EDT_MCP_RULES_REF` в `.dev.env` (только эту строку) и наличие файлов пакета (`ROUTER.md`, `rules/<lang>/INDEX.md`). Всё на месте и согласовано → режим **repair**: уточни у пользователя, что чинить, и переходи сразу к нужному шагу. Маркер есть, файлов нет / версии в клиентских путях расходятся → **повреждённая установка**: пройди шаги 1–4 полностью (они синхронизируют состояние). Ничего нет → свежая установка, все шаги подряд.
2. **EDT-MCP отвечает?** Вызови `get_server_status`. Недоступен → не провал: предупреждение («плагин не отвечает — инструменты будут недоступны до запуска») и продолжай: файлы ставятся независимо от живого сервера.
3. **git есть?** `git --version`. Нет git → предложи ручную установку из архива релиза (см. «Ручная установка» ниже). Пользователь отказался и вручную ставить не будет → **останови весь workflow, ничего не записывай**: маркеры, ИБ-gate и блок стека ссылаются на файлы, которых без пакета не будет.
4. **Клиент(ы)?** Найди в корне проекта: `.agents/skills/`, `.claude/skills/`, `.cursor/`. Есть несколько — установка во все найденные; нет ни одного — создай `.agents/skills/` и сообщи о выборе. Раскладку под конкретный клиент (куда именно внутри каталога клиента) сверяй с README плагина из клона — он источник раскладки, этот workflow не дублирует матрицу клиентов.
5. Зафиксируй результат проверки одной строкой отчёта.

## Шаг 1. Установка пакета правил EDT-MCP

1. **Тег.** Порядок приоритета: тег, названный пользователем → значение конфигурации модуля, если задано → `GET https://api.github.com/repos/DitriXNew/EDT-MCP/releases/latest` → поле `tag_name`. Если API недоступен или ответ подозрителен — фолбэк `git ls-remote --tags https://github.com/DitriXNew/EDT-MCP.git`, последний тег по сортировке версий. Тег, названный пользователем, но не существующий ни в API, ни в `ls-remote` → стоп с перечнем доступных последних тегов.
2. **Сверка с минимумом.** Сравни тег с действующим минимумом (`edt_mcp_min_version` из конфигурации модуля либо `MIN_EDT_MCP_RULES_REF` ядра). Меньше → предупреждение и явное подтверждение ставить устаревший. Больше протестированного → предупреждение: пакет новее написанного модуля, при следующей активации ядро запросит подтверждение — ставить?
3. **Клон.** `git clone --depth 1 --branch <тег> https://github.com/DitriXNew/EDT-MCP.git <tmp>/edt-mcp-ref` во временный каталог вне проекта.
4. **Проверь целостность клона:** существуют `agent/skills/COMMON.md`, `agent/ROUTER.md`, `rules/<lang>/INDEX.md`. Нет → стоп: релиз без ожидаемого лейаута, сообщи пользователю, ничего не копируй.
5. **Скопируй в каждый клиентский каталог (шаг 0.4):**
   - все каталоги `agent/skills/edt-mcp-project-*` (сверься с фактическим числом в клоне — оно может отличаться от документации) → `<client-skills>/`;
   - `agent/skills/COMMON.md` → рядом с ними;
   - `agent/ROUTER.md` → `<project>/.agents/edt-mcp/ROUTER.md`.
   Повторная установка = **замена наших управляемых путей**: каталоги `edt-mcp-project-*`, отсутствующие в новом релизе, но оставшиеся от старого, удали; файлы пользователя без этого префикса не трогай.
6. **Правила:** скопируй `rules/<lang>/` в корень проекта как `<project>/rules/`; `<lang>` = значение конфигурации модуля `rules_lang`, иначе `ru`, иначе явно запрошенный пользователем `en`.
7. Удали временный клон. Запомни тег — он пойдёт в маркер.
8. **Проверь результат установки:** в каждом клиентском пути лежат скиллы + `COMMON.md`, на месте `<project>/rules/<lang>/INDEX.md` и `ROUTER.md`. Что-то отсутствует → сообщи точный список, не помечай установку успешной.

Имена каталогов скиллов не переименовывать: префикс `edt-mcp-project-*` — часть контракта маршрутизации.

## Шаг 2. Маркеры проекта (.dev.env)

Три ключа принадлежат модулю — их значения workflow **актуализирует** (в т.ч. после переустановки на другой тег); остальные ключи файла не трогает и нигде не выводит (учётные данные):

```
EDT_MCP_RULES_REF=<тег из шага 1>
IB_UPDATE_CHANNEL=edt-only
AI_RULES_SYNC_REF=e59525d042c1
```

`AI_RULES_SYNC_REF` — база сверки с апстримом ai_rules_1c (`comol/ai_rules_1c@e59525d042c1`, от которого конвертировано подмножество правил модуля); меняется только процессом обновления модуля.

## Шаг 3. Гейт ИБ в USER-RULES.md

Файл принадлежит пользователю: создаём при отсутствии; при наличии дописываем блок только между нашими маркерами. Никогда не переписываем чужой текст. Обновление формулировок гейта новой версией модуля — замена строго содержимого между маркерами.

```markdown
<!-- e1c:ib-gate:start -->
## Правило ИБ: обновление базы только через EDT (модуль e1c)

Обновление конфигурации информационной базы — только через EDT-MCP:
get_applications → update_database (+ set_infobase_credentials).
/update1cbase и пакетный Designer (1cv8.exe / ibcmd) для обновления БД вне EDT запрещены.
Исключение CI: пакетное обновление допустимо только как шаг пайплайна, недоступного агенту интерактивно.
Разрешены без обновления БД: create_infobase, выгрузка XML (export_configuration_to_xml), восстановление .dt в новую/тестовую ИБ.
Связь ветка ↔ ИБ — только set_branch_infobase.
<!-- e1c:ib-gate:end -->
```

## Шаг 4. Маркированный блок стека в AGENTS.md

Корневой `AGENTS.md` владеет BMAD-инсталлятор — работаем строго между маркерами, вне их ничего не создаём и не меняем. Файла нет → создай с единственной строкой `# AGENTS.md` перед блоком. Блок генерируем динамически: в списке доменных скиллов называем **только фактически установленные** в этом клиенте скиллы модуля — непостроенные не упоминаем.

```markdown
<!-- e1c:stack-block:start -->
## Стек 1C:EDT (модуль e1c) — читать всегда при работе с конфигурацией 1С

- Ядро контура и гейтов: скилл `e1c-core` — грузить вместе с любым `e1c-*`; контур
  «прочитал MCP → записал MCP → EDT зелёный», гейт версии пакета, ИБ-gate
  (обновление базы только get_applications → update_database), деструктивный gate.
- Правила EDT-MCP: `rules/<lang>/INDEX.md` (навигатор пакета, установленного из репозитория плагина).
- Задачная маршрутизация EDT-MCP: `.agents/edt-mcp/ROUTER.md` → скиллы `edt-mcp-project-*`.
- Проектные соглашения и гейты: `USER-RULES.md`.
- Доменные правила модуля: <перечень фактически установленных e1c-скиллов>.
<!-- e1c:stack-block:end -->
```

Английская ветка правил (шаг 1.6) → в блоке ссылка `rules/en/INDEX.md`.

**Стабы для клиентов, не читающих `AGENTS.md`:** Claude Code → строка-ссылка на блок в `CLAUDE.md` (если файл управляется другим инструментом — сообщи вместо записи); Cursor → та же строка в `.cursorrules` или `.cursor/rules/` согласно принятому в проекте формату; прочие клиенты — по их механизму корневых инструкций. Стаб — одна строка-указатель, никогда не копия блока.

## Ручная установка (без git)

1. Узнай тег: открой https://github.com/DitriXNew/EDT-MCP/releases (или спроси у пользователя).
2. Скачай Source code (zip/tar.gz) нужного тега, распакуй во временный каталог.
3. Выполни шаги 1.4–1.8 из распаковки, затем шаги 2–5 как обычно. Продолжение — с шага 2.

## Шаг 5. Чек-лист ручных шагов (выведи пользователю)

- Eclipse-плагин EDT-MCP установлен и запущен? (предупреждение из шага 0.2 — вот момент проверить)
- Расширение YAxUnit добавлено в целевую ИБ? Без него `run_yaxunit_tests` работать не будет.
- Клиент перезапущен? MCP-серверы и скиллы большинство клиентов читает при старте.
- Для веб-публикаций/UI-тестов: ИБ опубликована?

## Гигиена репозитория проекта

Сообщи команде проекта на выбор: закоммитить установленные деревья (`rules/`, `.agents/edt-mcp/ROUTER.md`, клиентские копии скиллов) как версионируемую часть проекта — или добавить их в `.gitignore` проекта и ставить каждому разработчику этим же workflow. Решение фиксируется в отчёте.

## Откат

Workflow не выполняет удаление. Для ручного отката в сводке перечислены все затронутые пути (файлы и блоки между маркерами) — их достаточно, чтобы удалить установку целиком; маркерные блоки вырезаются по маркерам, ключи `.dev.env` — по именам.

## Отчёт

Заверши сводкой: режим (свежая/repair), что установлено (тег, клиентские пути, число скиллов), какие маркеры записаны/актуализированы, что изменено в `USER-RULES.md`/`AGENTS.md` (или почему нет), полный перечень затронутых путей (для возможного отката), чек-лист ручных шагов, рекомендация по гигиене репозитория и строка `EDT tooling: get_server_status (rules ref <тег>)` — попытка проверки сервера была всегда.
