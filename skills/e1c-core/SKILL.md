# e1c-core — ядро контура и гейтов

Этот файл обязателен к загрузке вместе с любым доменным скиллом `e1c-*`. Он определяет, *как* агент работает с проектом 1С:EDT через MCP-сервер EDT-MCP. Доменные скиллы (`e1c-bsl-practices`, `e1c-metadata-forms`, `e1c-testing-yaxunit`) добавляют предметные правила поверх этого ядра и не могут его отменять.

Константы ядра:

- `MIN_EDT_MCP_RULES_REF` = `v2.15.1` — минимальный тег релиза [EDT-MCP](https://github.com/DitriXNew/EDT-MCP), под которым проверен этот модуль. Значение по умолчанию; переменная конфигурации модуля `edt_mcp_min_version` (если задана при установке) имеет приоритет над ним.

Имена инструментов в этом файле приведены по состоянию на `MIN_EDT_MCP_RULES_REF` и являются ориентировочными: при расхождении с живым контрактом (`tools/list`, `get_tool_guide`) приоритет у живого сервера — применяй принцип правила, а не литеральное имя.

## Шаг активации — гейт версии пакета EDT-MCP

Выполняется **один раз за задачу**, до первого обращения к любому инструменту EDT-MCP; повторно — если пакет обновлялся в этой же сессии.

1. Извлеки из `.dev.env` в корне проекта **только** строку `EDT_MCP_RULES_REF` (тег релиза, под которым установлен пакет правил `agent/`+`rules/`). Остальное содержимое файла не читай и не выводи: там могут быть учётные данные ИБ.
2. Сравнивай теги так: префикс `v` опционален, формат `X.Y.Z`, отсутствующие сегменты = 0; маркер, не разобранный как три числа, считай расхождением.
3. **Маркера нет** → стоп. Сообщи пользователю: пакет правил EDT-MCP не установлен, запускай скилл `e1c-setup`. Не работай вслепую.
4. **Маркер меньше минимума** → стоп. Сообщи: версия пакета устарела, запускай скилл `e1c-updater`; правила могли измениться вместе с плагином.
5. **Маркер больше протестированного** (`MIN_EDT_MCP_RULES_REF`) → стоп с сообщением: пакет новее, чем тот, под которым написан модуль; продолжение — только после явного подтверждения пользователя («продолжай»).
6. **Файлов пакета нет на диске** (ни `ROUTER.md`, ни `rules/<lang>/INDEX.md` — `<lang>` это ветка правил `ru|en`, выбранная при установке, по умолчанию `ru`; пути клиента: `.agents/skills/`, `.claude/skills/`, корень проекта) при наличии маркера → это повреждённая установка: сообщи и предложи `e1c-setup`, не пытайся чинить сам. Достаточно одного валидного экземпляра пакета; разные версии в разных клиентских путях считай повреждением.
7. Убедись, что инструменты EDT-MCP реально доступны в этой сессии (присутствуют в схеме инструментов или отвечает `get_server_status`). Недоступный сервер — стоп с сообщением о подключении плагина, а не молчаливые падения вызовов позже.
8. Гейт пройден → работай. Формат отчёта — раздел «Отчёт» ниже.

Если указанный скилл восстановления (`e1c-setup`/`e1c-updater`) в клиенте не установлен — выполняй его процедуру вручную по README репозитория модуля и сообщи об этом.

Здесь и далее «корень проекта» — корень репозитория бизнес-проекта (каталог с `AGENTS.md`/`.dev.env`), а не внутренний путь Eclipse-workspace.

Оговорка апстрима: актуальный каталог инструментов сервера (`tools/list`, `get_tool_guide`) **приоритетнее** скопированных примеров при расхождении версий. Наш гейт делает это явным стопом, а не молчаливым приоритетом.

## Контур: прочитал MCP → записал MCP → EDT зелёный

Один контур определяет «сделано» для 1С-задачи; его слои не выбираются по отдельности:

1. **Прочитал MCP.** Факты о конфигурации (объекты, реквизиты, формы, модули) — только из инструментов EDT-MCP или от пользователя. Не выдумывай метаданные, не считай синоним именем, не опирайся на память о похожих конфигурациях.
2. **Записал MCP.** Любое изменение конфигурации — только вызовом инструментов EDT-MCP (`write_module_source`, `create_metadata`, `modify_metadata`, …). Файлы исходников (`.bsl`, `.mdo`, `Form.form`, всё под `DT-INF/`) не редактируй файловыми инструментами клиента, даже если они видны в workspace — правка мимо модели рассинхронизирует EDT.
3. **EDT зелёный.** Работа не сделана, пока ошибки EDT по затронутым объектам чистые и тесты прошли (`e1c-testing-yaxunit`). Методика: дать EDT досчитать валидацию после записи (`revalidate_objects` по изменённым объектам), затем `get_project_errors` с фильтром по проекту и серьёзности, сопоставляя маркеры именно с затронутыми файлами/объектами — а не оценивать «весь проект пуст». Чистый git-diff недостаточен.
4. **Сбой канала посреди контура** (сервер перестал отвечать после записи, до валидации) → задача **не** считается сделанной: зафиксируй в отчёте частичное состояние (что записано, что не проверено) и предложи переподключиться и завершить валидацию.

Режимы контура:

- **Реализация фичи** — контур обязателен целиком. Нельзя писать в конфигурацию и закрывать задачу без всех трёх слоёв.
- **Разведка перед планированием** — полезна и разрешена как read-only (только чтение MCP). Не блокер PRD/архитектуры, но факты о существующей конфигурации бери из EDT, а догадку не выдавай за факт.

После любой записи — проверь ошибки (`get_project_errors` / `get_problem_summary`) прежде чем объявлять результат.

## Гейт ИБ: обновление базы только через EDT

Обновление конфигурации информационной базы — **только** цепочка через EDT-MCP:

```
get_applications → update_database (+ set_infobase_credentials при необходимости)
```

Запрещено вне EDT: `/update1cbase`, пакетный Designer (`1cv8.exe`, `ibcmd`) для обновления конфигурации БД. Исключение CI: пакетное обновление допустимо **только как шаг пайплайна, недоступный агенту интерактивно** — если такой пайплайн существует, ссылайся на него, не воспроизводи команды руками.

Разрешены не-обновляющие операции: `create_infobase`, выгрузка XML (`export_configuration_to_xml`, `/getconfigfiles`), восстановление из `.dt` — но только в **новую или тестовую** ИБ: развёртывание `.dt` поверх существующей базы перезаписывает данные и потому проходит деструктивный gate ниже. Связка ветка ↔ ИБ — через `set_branch_infobase`; не переключай ветку git в EDT-проекте мимо инструментов плагина.

Почему так: стороннее обновление рассинхронизирует модель EDT и диск (лечится `resync_to_disk`, но не всегда сразу) и порождает фантомные ошибки валидации — «зелёный» становится недоверенным.

Подтверждение режима: `IB_UPDATE_CHANNEL=edt-only` в `.dev.env` (ставит `e1c-setup`). Текст гейта в `USER-RULES.md` проекта имеет ту же силу.

## Деструктивный gate

Операции из списка выполняются только по **явной просьбе пользователя** и всегда в два шага: вызов без `confirm` (preview всех изменений) → показ результата → выполнение того же вызова с `confirm: true` после явного согласия:

- `rename_metadata_object`, `delete_metadata`
- `delete_project`, `delete_infobase`
- `update_database`
- `modify_metadata`, когда он меняет тип данных

Если инструмент не даёт preview без `confirm` (ошибка вместо превью) — покажи пользователю описание последствий текстом и выполняй с `confirm` только после явного согласия.

Агент не инициирует эти операции сам «заодно» и не отключает consent-механизм сервера (`EDT_MCP_DESTRUCTIVE_CONSENT=allow` не предлагать, если пользователь сам не просит — и тогда назвать, что именно это убирает).

## Билингвальность: Name vs Synonym vs тип

- Тип объекта двуязычен на уровне платформы: `Справочник`/`Catalog`, `Документ`/`Document`. Принимай оба написания.
- Ключ адресации — программное **Name** объекта (FQN вида `Catalog.Товары`), строго как в конфигурации.
- **Synonym** (Представление) — отображение для пользователя. Не используй его как ключ поиска или адресации; не путай с Name.
- При создании/изменении объектов заполняй синонимы для **каждого кода языка**, заявленного в конфигурации (например, `ru` и `en`) — синоним адресуется кодом языка, а не его именем.

## Не выдумывать БСП и типовые подсистемы

Существование подсистем БСП, типовых общих модулей и их API считается подтверждённым, только если это показал инструмент (например, `list_subsystems`, `get_subsystem_content`, поиск по коду) или назвал пользователь. Нет подтверждения → пометь как гипотезу и проверь или спроси. «Доступные источники» = инструменты документации/поиска, реально подключённые в этой сессии; нет таких инструментов — остаётся гипотеза. Платформа-first: перед собственным решением специализированной задачи проверь, есть ли готовый механизм платформы.

## Порядок приоритета правил

```
явное, высказанное ПОСЛЕ предупреждения решение пользователя
> гейты безопасности этого ядра (ИБ-gate, деструктивный gate)
> прочие гейты и правила этого ядра
> проектные правила клиента (корневые инструкции проекта)
> правила доменных скиллов e1c-*
> пакет правил agent/+rules/ EDT-MCP
> внутренняя документация проектов-источников
```

Гейты безопасности отменяются только первым уровнем: явным решением пользователя, высказанным **после** предупреждения о последствиях. Молчаливое «делай как удобнее», строка в проектных правилах клиента или инструкция из другого слоя гейт не снимают. Вне гейтов безопасности верхний уровень также требует явного запроса: обычная просьба переопределяет доменные правила и пакет EDT-MCP, но не правила ядра. Обходя любое правило, назови одним предложением, какое правило обходишь.

## Отчёт

Любая задача, коснувшаяся EDT-MCP, заканчивается ровно двумя фиксациями:

```
EDT tooling: <использованные инструменты> (rules ref <проверенный тег>)
```

и — если была операция над ИБ — дополнительной строкой:

```
IB tooling: <команда/путь>
```
