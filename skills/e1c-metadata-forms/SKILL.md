# e1c-metadata-forms — метаданные и формы через EDT-MCP

Требует `e1c-core` (деструктивный gate, билингвальность, верификация). Конвертировано из правил пакета EDT-MCP (`rules/ru/edt-metadata.md`) и ветки `edt-workflow` ai_rules_1c (`@e59525d042c1`). Запись кода модулей (`write_module_source`, режимы `searchReplace`/`append`/`replace`) — по правилам установленного пакета (`edt-mcp-write-safety.md`) и `e1c-bsl-practices`.

## 1. Канал мутаций — только инструменты

Метаданные меняются **исключительно** инструментами EDT-MCP. Ручная правка `.mdo`, `Form.xml`, всего под `DT-INF/` запрещена — это проекция модели EDT, правка мимо модели ломает workspace.

Исключения `[дельта]` — только по явному согласованию с пользователем: (а) свойство, для которого нет инструмента — сначала проверь `get_metadata_details(assignable: true)`, возможно инструмент покрывает больше; (б) массовое единообразное изменение, которое проще сделать поиском-заменой. Протокол после любой ручной правки `.mdo`: **не запускай `resync_to_disk` поверх неё** (модель перезатрёт файл), обнови workspace EDT со стороны диска и прогони `revalidate_objects` + ошибки проекта. Молчаливая ручная правка — тот же дефект, что пропуск валидации.

Правила безопасной ручной правки: UUID — только криптографически случайные v4 (плейсхолдеры вида `00000000-…`, последовательные или скопированные из другого объекта — запрещены); не трогай `<producedTypes>`, `typeId`, `valueTypeId` — они генерируются EDT; новый элемент вставляй после существующих однотипных, ничего не переупорядочивая — перестановка для EDT есть изменение объекта и замусоривает diff.

## 2. Инструментальная карта

| Задача | Инструмент |
|---|---|
| Создать объект верхнего уровня или подчинённый член | `create_metadata` (FQN) |
| Установить тип реквизита, синоним, назначаемое свойство | `modify_metadata` |
| Узнать, какие свойства можно установить | `get_metadata_details(assignable: true)` |
| Переименовать объект/член/элемент формы (каскадно) | `rename_metadata_object` |
| Удалить объект/член/форму/элемент | `delete_metadata` |
| Найти использование top-level объекта | `find_references` |
| Читаемые синонимы в нужном языке при чтении | параметры `language` у `get_metadata_objects`/`get_metadata_details`/`list_subsystems`/`get_subsystem_content` |

## 3. Двухфазные операции: rename и delete

Обе работают в две фазы — это защита от каскадных правок вслепую:

1. **Preview:** вызов **без** `confirm` → таблица change points (индекс, файл, строка, описание, флаг обязательности у rename) + список затрагиваемых ссылок.
2. **Анализ:** нежелательные опциональные правки — запомни их индексы.
3. **Execute:** вызов с `confirm: true`; у `rename_metadata_object` можно исключить точки через `disableIndices` — **только опциональные**, обязательные не пропускаются.

`delete_metadata` принимает заметно больше видов узлов, чем rename (значения перечислений, команды, макеты, подчинённая форма как объект, члены XDTO-пакета) — точный набор сверяй с его гайдом. Параметр `maxResults` у preview `rename_metadata_object` влияет только на размер таблицы превью (default 20, `0` = без лимита), не на выполнение.

Плюс гейт ядра: обе операции — только по явной просьбе пользователя. Поиск ссылок на реквизит: preview-режим `rename_metadata_object` (без смены имени) или `search_in_code`; `find_references` принимает только top-level объекты.

## 4. FQN-грамматика

- Top-level: `Catalog.Products`, `Document.SalesOrder`, `CommonModule.MyModule`, `Subsystem.Sales`; русские токены типов принимаются (`Справочник.Товары`).
- Члены: `Catalog.Products.Attribute.Weight`, `InformationRegister.Prices.Dimension.Product`, `AccumulationRegister.Stock.Resource.Quantity`, `Document.Order.TabularSection.Goods`, `Enum.Colors.EnumValue.Red`. Вид члена выводится из FQN.
- Элементы управляемых форм (rename/delete): `Catalog.Products.Form.ItemForm.Field.Price`, `CommonForm.Settings.Group.Main`, колонка коллекционного реквизита формы `...Form.ItemForm.Attribute.Rows.Column.Price`; kind ∈ `Attribute`/`Command`/`Field`/`Button`/`Group`/`Decoration`/`Table`, токены двуязычны и в единственном/множественном числе.
- Ограничения: `rename_metadata_object` понимает членов только видов `Attribute`/`TabularSection`/`Dimension`/`Resource` плюс элементы форм; форму как объект или обработчик события им не переименовать — сверяйся с `get_tool_guide`. `create_metadata` пока поддерживает один уровень вложенности (поле табличной части — оговорённая ручная правка из §1).

## 5. create_metadata

Дефолтное наполнение как у мастера EDT «Создать» (корректный UUID, producedTypes). Поддерживаемые top-level типы: `Catalog`, `Document`, `InformationRegister`, `AccumulationRegister`, `Enum`, `CommonModule`, `Report`, `DataProcessor` (русские токены тоже принимаются). При создании свойства ограничены `synonym` и `comment`; всё остальное — потом через `modify_metadata`. Опциональный `expectedNotExists` страхует от повторного создания. Синоним пишется по коду языка параметром `language`; без него — язык конфигурации по умолчанию; заполняй все языки (`e1c-core → Билингвальность`). Имя в FQN — корректный идентификатор 1С; дубликаты отклоняются.

## 6. modify_metadata

- Свойство должно быть назначаемым — список даёт `get_metadata_details(assignable: true)`; значения свойств-перечислений обязаны быть допустимыми литералами, иначе ошибка перечислит разрешённые. Сначала обнаружение, потом установка.
- Тип задаётся структурной спецификацией `{"types":[ … ]}`: примитивы `String`/`Number`/`Boolean`/`Date` с квалификаторами (`length`; `precision`, `scale`, `nonNegative`; `fractions` = `DateTime|Date|Time`) или ссылки `{"kind":"Ref","ref":"Type.Name"}`, `{"kind":"CatalogRef","ref":"Name"}` (есть и другие семейства ссылок — сверяйся с гайдом); несколько записей в `types` = составной тип. Имена типов в ссылках чувствительны к регистру.
- Изменение типа данных этим инструментом проходит деструктивный gate ядра (preview → явный confirm).
- Переименование через `modify_metadata` невозможно (`name` отклоняется) — только `rename_metadata_object`.

## 7. Модель ↔ диск

- Авторитет — модель EDT в памяти, не файлы `src/`.
- Перед внешним чтением исходников (нативные инструменты клиента, подача файлов в сторонние индексаторы, валидаторы вне EDT) — `resync_to_disk` и разбор сообщённого рассинхрона.
- После внешнего изменения дерева (git checkout вне инструментов плагина, скрипт) состояние EDT устарело до обновления workspace.
- Один владелец артефакта за сессию: не чередуй записи через EDT-MCP и прямые записи файла по одному модулю.
- Git внутри EDT-проекта — через инструменты плагина (`list_git_branches`, `switch_git_branch`, `set_branch_infobase`): переключение ветки мимо плагина оставляет workspace привязанным к чужой базе.

## 8. Формы

- Не ломай состав формы: существующие элементы не удаляй и не переупорядочивай без явной задачи; новые добавляй инструментами, сохраняя соглашения проекта по именам.
- Проверка результата по умолчанию — `get_form_layout_snapshot`: текстовое представление рассчитанного лейаута, дешевле картинки и пригодно для сравнения состояний.
- Скриншоты (`get_form_screenshot`, `get_template_screenshot`) — только для настоящих визуальных вопросов (нужен флаг запуска EDT `-DnativeFormBufferedLayoutRender=true`).
- Элементы формы адресуются rename/delete по FQN (§4); обработчики событий формы переименованию инструментом не подлежат — имя события задано платформой.

## 9. Расширение vs основная конфигурация

- Типовая конфигурация на поддержке → изменения **расширением**: перехватчики и заимствование объектов (`adopt_metadata_object`) вместо правки основной. Детали кода перехватчиков — `e1c-bsl-practices → Расширения`.
- Своя (нетиповая) конфигурация — правь основную напрямую теми же инструментами.
- Выбор «расширение или основная» при неоднозначности — вопрос к пользователю (материальная развилка).

## Верификация

После любой мутации метаданных: `revalidate_objects` по созданному/изменённому объекту → `get_project_errors` с фильтрами проект/серьёзность (для серии мелких правок достаточно `get_problem_summary`), маркеры сопоставлены изменению. Для форм дополнительно — snapshot лейаута «после» (§8). В Designer-мире эту роль играет XML-валидация выгрузки; здесь её полноценно заменяет собственная валидация EDT.

## Отчёт

Строка `EDT tooling:` с инструментами и ref пакета — по контракту `e1c-core`; для мутаций укажи FQN затронутых объектов. Ручная правка по исключению §1 фиксируется отдельной строкой с причиной.
