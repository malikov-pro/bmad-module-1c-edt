# 1C EDT — BMad-модуль (`e1c`)

Модуль-расширение [BMad Method](https://github.com/bmad-code-org/BMAD-METHOD) (поверх `bmm`), который добавляет в BMAD-цикл 1С-линзу: проектировать и реализовывать решения на платформе 1С так, что чтение и изменение конфигурации идут **только через EDT-MCP**, а работа считается сделанной, когда **EDT зелёный** — ошибки по затронутым объектам чистые и тесты YAxUnit прошли.

Один контур, не три фичи: **прочитал MCP → записал MCP → EDT зелёный**.

**Статус:** в разработке (фаза планирования — см. [`skills/reports/module-plan-1c-edt.md`](skills/reports/module-plan-1c-edt.md)).

## Стек: четыре слоя

Модуль — прослойка учёта стека «1С + EDT + EDT-MCP» внутри BMAD. Методология остаётся BMAD; модуль подмешивает правила работы со стеком в контур setup / build / review.

| Слой | Роль | Источник | Что берём |
|---|---|---|---|
| **L0 Исполнение** | Все операции с метаданными, кодом и ИБ | [DitriXNew/EDT-MCP](https://github.com/DitriXNew/EDT-MCP) | Плагин для 1C:EDT — HTTP MCP-сервер (~89 инструментов). Прогрессивное раскрытие: пресет Development; для ревью-агентов Analysis Only |
| **L1 Правила** | Канонические стандарты BSL, верификация | [comol/ai_rules_1c](https://github.com/comol/ai_rules_1c) | Установка в проект через `AGENT-INSTALL.md`; при `USE_EDT=true` включается ветка `edt-workflow.md` (маршрутизация MCP-комплект ↔ EDT-MCP + гейты процесса) |
| **L2 Оркестрация** | Порядок работ, тестовый контур, ревью | [SteelMorgan/1c-agent-based-dev-framework](https://github.com/SteelMorgan/1c-agent-based-dev-framework) | Выборочно: песочница (docker), цикл SDD+TDD (спека → YAxUnit-тесты → код → прогон), кросс-ревью вторым агентом, тиринг моделей. Его coding-standards НЕ ставим — дубль ai_rules_1c |
| **L3 Процесс** | Бриф → PRD → архитектура → эпики/стори | [bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD) | Установка `npx bmad-method install`. Стори BMAD — вход 1С-пайплайна L2 (OpenSpec-спека → тесты → код через EDT-MCP → ревью) |

Матрица владения:

- требования / PRD / архитектура — **BMAD** (L3);
- спеки задач / стандарты BSL / верификация — **ai_rules_1c** (L1);
- порядок работ / тестовый контур / ревью — **фреймворк SteelMorgan** (L2);
- все операции с метаданными / кодом / ИБ — **EDT-MCP** (L0).

### Приоритет правил

- **EDT-MCP `rules/<lang>/INDEX.md`** (8 модулей; обновляются синхронно с плагином) — *как выполнять инструменты*.
- **ai_rules_1c `edt-workflow.md`** — *какой комплект MCP когда + гейты процесса*.
- Корневой `AGENTS.md` бизнес-проекта ведёт установщик ai_rules_1c; ссылка на `rules/<lang>/INDEX.md` EDT-MCP вписывается внутрь него — отдельный корневой файл не создаётся.

Для бизнес-проектов из репозитория EDT-MCP ставятся `agent/` (13 скиллов `edt-mcp-project-*` + `ROUTER.md` + `COMMON.md`) и `rules/`. Контрибьюторские файлы самого плагина (корневой `CLAUDE.md`, `.claude/`) в бизнес-проекты **не** ставятся — они нужны только при разработке самого EDT-MCP.

### Инвариант: ИБ обновляется только через EDT

Обновление конфигурации БД — только цепочка `get_applications` → `update_database` (+ `set_infobase_credentials`) через EDT-MCP.

Запрещены `/update1cbase` и пакетный Designer для обновления БД вне EDT: стороннее обновление рассинхронизирует модель EDT и диск (нужен `resync_to_disk`) и порождает фантомные ошибки валидации.

Разрешены не-обновляющие операции: `create_infobase`, восстановление из `.dt`, выгрузка XML (`export_configuration_to_xml`). Связка ветка ↔ ИБ — через `set_branch_infobase`.

Фиксация: текст гейта — в `USER-RULES.md` (ai_rules_1c его не перезаписывает); маркер `IB_UPDATE_CHANNEL=edt-only` в `.dev.env`; `PLATFORM_PATH`/`INFOBASE_*` сохраняются — они нужны разрешённым командам. Исключение CI без EDT: пакетное обновление допустимо только как шаг пайплайна, недоступный агенту интерактивно.
