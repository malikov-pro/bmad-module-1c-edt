## Как работает AGENT-INSTALL.md (ai_rules_1c)?

*Вопрос: 2026-08-24*

Это протокол установки правил `ai_rules_1c` в бизнес-проект, который выполняет **сам ИИ-агент** (читает документ и делает раскладку файлов). Второй канал — PowerShell-скрипт `install.ps1`: тот же протокол детерминированно, для CI/ограниченных сред.

Ключевые механизмы:

1. **Только project root.** Правила проектные; установка в глобальные каталоги CLI (`~/.claude`, `~/.codex`, …) запрещена. Если агент запущен в «анонимном» каталоге — обязан остановиться и спросить путь.
2. **Lean placement.** Агент не читает тела всех правил (экономия токенов): он читает только маленькие `adapters/<tool>.yaml` — там описано, как детектировать инструмент, куда копировать секции (`rules/agents/commands/skills`), какие преобразования frontmatter делать и как рендерить конфиг MCP под конкретный клиент.
3. **Always-on слой в корне проекта:** `AGENTS.md` (рендерится с перезаписью путей под активный инструмент: `content/rules/x.md` → `.cursor/rules/x.mdc` и т.п.), плюс `USER-RULES.md`, `memory.md`, `LLM-RULES.md`.
4. **`.dev.env`** — единый источник параметров проекта (платформа, ИБ, префиксы, модели субагентов). Вопрос «используется ли EDT?» (`USE_EDT`) задаётся один раз при создании файла. Существующий файл установщик не трогает.
5. **Manifest `.ai-rules.json`** — перечень установленных файлов с хэшами. При обновлении всё, что пользователь менял вручную, сохраняется (`userModified`); есть аварийный `-ForcePaths`.
6. **Миграция:** если в проекте уже был свой `AGENTS.md`/`CLAUDE.md`, он переименовывается в `.bak.md`, а содержимое инлайнится в `USER-RULES.md` между маркерами.
7. После установки агент предлагает меню `/installtools` — там же предлагается установка **EDT-MCP** как опционального инструмента.

Источник: `_sources/ai_rules_1c/AGENT-INSTALL.md`.

## Почему гейт «ИБ только через EDT» кладём в USER-RULES.md?

*Вопрос: 2026-08-24*

Потому что у файлов разное владение:

- `AGENTS.md` установщик **переписывает** при каждом update (пока файл не изменён пользователем вручную) — наша правка может исчезнуть.
- `USER-RULES.md` создаётся один раз и **никогда не перезаписывается**; при этом агенты читают его вместе с `AGENTS.md` — то есть это полноценная часть always-on контекста. В нём же документирован механизм `@-imports` дополнительных файлов.
- `.dev.env` установщик тоже никогда не перезаписывает — туда спокойно дописывается наш маркер `IB_UPDATE_CHANNEL=edt-only`.

Источник: `_sources/ai_rules_1c/AGENT-INSTALL.md` → разделы *File ownership*, *USER-RULES.md*.

## Из чего состоит EDT-MCP для бизнес-проектов?

*Вопрос: 2026-08-24*

Два комплекта, ставятся из репозитория плагина (обновляются синхронно с ним):

- **`rules/<lang>/`** (ru|en) — постоянная политика: INDEX-навигатор + всегда читать (common-safety, карта инструментов 9 групп, write-safety, workflows, token-economy, metadata) + по ситуации bsl-coding-style (+опционально bsl-ssl для БСП).
- **`agent/`** — маршрутизация задач: `ROUTER.md` ведёт на 13 скиллов `edt-mcp-project-*` (session, code-research, local-fix, metadata, forms, query-dcs, external-objects, runtime-debug, yaxunit, maintenance, profiling, workmate, translation) + `COMMON.md` + `TOOL_CAPABILITY_MATRIX.md`. Принцип: загружать самый маленький подходящий скилл.

Корневые `CLAUDE.md` и `.claude/` репозитория EDT-MCP — контрибьюторские (для разработки самого плагина), в бизнес-проекты не идут.

Источник: `_sources/EDT-MCP/{agent,rules}`.

## Что уже покрывает ai_rules_1c, чтобы модуль не дублировал?

*Заметка: 2026-08-24*

- **BSL-стандарты и верификация**: 46 on-demand правил (`content/rules/`), цепочка валидаторов `syntaxcheck → check_1c_code → review_1c_code`, бюджеты проверок, триаж quick-fix/full-cycle/spec-authoring.
- **SDD**: OpenSpec-workspace ставится его установщиком, правила работы — `sdd-integrations.md`.
- **Тиринг моделей**: `/economymode` + `SUBAGENT_MODEL_*` + `subagent-pipeline.md` (родитель делегирует дешёвым субагентам по ярусам).
- **EDT-ветка**: `edt-workflow.md` при `USE_EDT=true` — уже содержит маршрутизацию EDT-MCP, правило model↔disk (`resync_to_disk`), запрет ручных правок `.mdo/.form/DT-INF`, consent на destructive-операции.

Поэтому от SteelMorgan (L2) берём только недостающее: песочницу, кросс-ревью вторым агентом, политики изоляции тестов. Детали — Q3 в [todo.md](todo.md).

## Что значит «живой контракт MCP vs версионируемый playbook»?

*Вопрос: 2026-08-24*

Проблема: наш модуль должен учить агента работе с EDT-MCP, но EDT-MCP — живой сторонний плагин. Сегодня у него ~89 инструментов; завтра станет 95 или 82, изменятся имена и параметры. Его репозиторий даже содержит `rules/` и `agent/`, которые автор обновляет синхронно с релизами плагина.

Есть два способа описать «как звать инструменты» внутри нашего модуля:

**A. Версонируемый playbook** — скопировать описание инструментов к себе («`create_metadata` принимает FQN и свойства…») и хранить в скиллах модуля.
- Плюс: стабильно, всё под рукой.
- Минус: **устаёт**. Плагин обновился — наша копия врёт: агент зовёт несуществующий инструмент или передаёт старые параметры. Придётся отслеживать каждый релиз плагина и переписывать модуль. Это и есть проблема «форк CLAUDE.md навсегда», от которой мы уходили ещё на идеации.

**B. Живой контракт** — источник правды об инструментах всегда сам инструмент:
- во время работы агент читает актуальный список из MCP: `tools/list`, а по спорным параметрам — `get_tool_guide`;
- правила вызова и безопасности берутся из комплекта `rules/<lang>/` + `agent/`, установленного из репозитория плагина (он обновляется вместе с плагином, рассинхрона нет).

Минус B: если плагин не установлен, агенту не на что опереться.

**На практике берём гибрид «двух темпов»:**

| Слой | Как быстро меняется | Где живёт |
|---|---|---|
| Имена/параметры инструментов | каждое обновление плагина | нигде не версонируем: сервер (`tools/list`, `get_tool_guide`) |
| Правила вызова, безопасность записи | синхронно с релизами плагина | комплект `rules/`+`agent/` из репо плагина, ставится в проект |
| Принципы и процесс модуля | медленно (годы) | скиллы `e1c-*`: контур «прочитал MCP → записал MCP → EDT зелёный», гейт ИБ, BSL-практики, требование YAxUnit |

Пример: модуль говорит «перед правкой метода прочитай его, после записи проверь ошибки проекта». Это принцип (медленный слой) — он не устареет. А *какие именно* инструменты для этого звать сегодня, агент уточняет по живому контексту или по установленному пакету правил плагина.

Репозиторий в `_sources/EDT-MCP` нужен нам на этапе **разработки модуля** (читать контракт, сверять находки); в рантайме бизнес-проекта носитель актуального контракта — установленный пакет `rules/agent` + живой сервер.

## Как устроены лицензии источников стека?

*Вопрос: 2026-08-24*

| Источник | Лицензия | Следствие для модуля |
|---|---|---|
| EDT-MCP | AGPL-3.0 | Не встраиваем код; взаимодействие через публичный MCP-интерфейс установленного плагина |
| ai_rules_1c | формальной нет («берите и используйте») | Не копируем содержимое в репозиторий модуля; установка родным установщиком |
| SteelMorgan fw | MIT заявлен в README, файла LICENSE нет | Берём практики процесса, не код |
| BMAD-METHOD | MIT + товарные знаки BMad Code, LLC | Модуль независимый, не официальный продукт; скиллы называем `e1c-*`, а не `bmad-*` |
| YAxUnit | Apache-2.0 | Расширение в целевую ИБ |

Принцип модуля: **ссылаться, а не копировать** — держит лицензии чистыми и контент актуальным.
