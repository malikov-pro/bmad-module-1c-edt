## Интеграция слоёв

### Q1. Владение корневым `AGENTS.md` — конфликт двух установщиков
- **Решение (2026-08-24):** владелец корневого `AGENTS.md` — **BMAD**; остальные слои (ai_rules_1c, EDT-MCP rules) его **дополняют**, но файл не переписывают.
- **Следствие → Q11:** нужно продумать механику дополнения, при которой 1С-правила применяются всегда, в т.ч. когда BMAD-ветка не стартует.
- **Статус:** закрыт · 2026-08-24

### Q11. Always-on применение 1С-правил вне BMAD-сессий
- **Суть:** обычная кодинг-сессия (Cursor/Claude Code/OpenCode без вызова `bmad-build` и др. скиллов BMAD) тоже обязана работать под 1С-правилами. Гарантию даёт не BMAD (он стартует только со своими скиллами), а сам клиент: он читает корневой файл инструкций при старте любой сессии.
- **Кандидат-механика:** `AGENTS.md` (владеет BMAD) содержит **маркированный блок стека** (стабильные маркеры begin/end), который ведёт setup-скилл модуля: внутри — указатели «читай всегда»: EDT-MCP `rules/<lang>/INDEX.md`, канонический каталог правил ai_rules_1c (`rules-1c`), `USER-RULES.md` (гейты, включая ИБ-gate). Для клиентов, не читающих `AGENTS.md` (например Claude Code читает `CLAUDE.md`) — минимальные стабы-заглушки со ссылкой на тот же блок. Нативные always-on каталоги (`.cursor/rules/*.mdc` с `alwaysApply`) используются там, где есть.
- **Открытые подпункты:**
  - ~~update ai_rules_1c без перезаписи корневого файла~~ **Решено (2026-08-24):** динамического импорта нет. Контент ai_rules_1c **конвертируется/копируется в модуль** под наши задачи (EDT-совместимое подмножество, см. Q9) и дальше живёт по нашему релизному циклу. Обновления от апстрима — **периодической задачей пользователя**: «посмотри коммиты ai_rules_1c с даты последней сверки, что применимо у нас». База для сверок зафиксирована: `comol/ai_rules_1c@e59525d042c1` (2026-08-24). Установщик ai_rules_1c как канал поставки больше не используется → конфликт с корневым `AGENTS.md` исчезает;
  - кто пишет маркированный блок стека: setup-скилл модуля (idempotent, merge-safe);
  - формат блока, совместимый с BMAD-инсталлятором (чтобы его перегенерация блока не затирала).
- **Статус:** открыт · 2026-08-24

## Решения и следующие за ними задачи

### Q9. Состав L1: из ai_rules_1c — только EDT-совместимое; его MCP-серверы — отдельными задачами
- **Решение (2026-08-24):** из ai_rules_1c в модуль берём то, что может использоваться с EDT (edt-workflow ветка, BSL-правила, субагенты, дисциплина памяти). Его собственный MCP-комплект (`1c-graph-metadata-mcp`, `1c-code-metadata-mcp`, `1C-docs-mcp`, `1c-syntax-checker-mcp`, `1c-templates-mcp`) признаётся **более функциональным**, чем аналоги, и подключается позже: пользователь формирует функционал MCP-серверов отдельными задачами и дополняет текущий проект наработками ai_rules_1c.
- **Открытые подпункты:**
  - порядок фаз: какие серверы первыми (кандидат: syntax-checker для верификации, graph/code-metadata для поиска);
  - влияние на цепочку верификации: сейчас «зелёный» = ошибки EDT (`get_project_errors`, `revalidate_objects`) + YAxUnit; с подключением серверов добавляется `syntaxcheck → check_1c_code → review_1c_code` из L1 — зафиксировать, какой слой чем владеет на каждом этапе;
  - стыковка с `mcp-first-search.md` (маршрутизация поиска index-MCP ↔ EDT-MCP) в `edt-workflow.md`.
- **Статус:** решение принято, реализация — отдельными задачами · 2026-08-24

### Q10. Гейт версии пакета EDT-MCP + скилл/скрипт обновления
- **Решение (2026-08-24):** добавляем в модуль два элемента:
  1. **Правило-гейт:** перед работой с EDT-MCP сверять версию установленного пакета `agent/`+`rules/` с версией, на которую рассчитан текущий модуль; при расхождении — **прекратить работу** и вывести пользователю сообщение (с указанием, как обновить).
  2. **Скилл/скрипт обновления:** процедура подтягивания свежего пакета из `DitriXNew/EDT-MCP`: получить актуальный ref → установить `agent/skills/*` + `COMMON.md` + `ROUTER.md` и `rules/<lang>/` по схеме из README плагина (пути зависят от клиента: `.agents/skills`, `.claude/skills`, …) → зафиксировать новую версию → повторно пройти гейт.
- **Открытые подпункты:**
  - ~~чем мерить версию~~ **Решено (2026-08-24):** версия пакета = **тег релиза EDT-MCP** (`vX.Y.Z`, например `v2.15.1`). Источник — GitHub API: `GET /repos/DitriXNew/EDT-MCP/releases/latest` → `tag_name`; тело релиза («What's Changed», список PR) используем как отчёт об изменениях при обновлении. Релизы частые (~каждые 2–4 дня) — гейт актуален. Установка пакета фиксируется на теге (clone/fetch `--branch <tag>` или tarball); setup пишет установленный тег в маркер проекта (`EDT_MCP_RULES_REF=v2.15.1` в `.dev.env`), модуль хранит минимально поддерживаемую версию;
  - где выполняется сверка: шаг активации скиллов `e1c-*` (дёшево, один раз за задачу), а не перед каждым вызовом инструмента;
  - поведение при отсутствии пакета вовсе: отдельная ветка — сообщение с установочной инструкцией, не «расхождение»;
  - учесть оговорку самого плагина: «current client catalog / `get_tool_guide` outrank copied examples when the installed server differs from this repository version» — наш гейт превращает молчаливый приоритет живого контракта в явный стоп.
- **Статус:** решение принято, механика — на проработку · 2026-08-24

## Открытые вопросы плана модуля (Phase 2, из `skills/reports/module-plan-1c-edt.md`)

### Q5. Подтвердить модель «прослойка стека» как архитектуру MVP
- **Решение (2026-08-24):** подтверждаю. Модуль — прослойка учёта стека «1С + EDT + EDT-MCP» внутри BMAD, по аналогии с тем, как BMAD учитывает стек через архитектуру и `AGENTS.md` / project-context. Методология (PRD → stories → build → review) остаётся BMAD; модуль подмешивает 1С-правила в контур setup / build / review. Не вторая методология, не замена BMAD.
- **Статус:** закрыт · 2026-08-24

### Q6. Живой контракт MCP vs версионируемый playbook
- **Суть:** см. развёрнутое объяснение в [notes.md](notes.md). Кратко: копировать описания инструментов EDT-MCP в модуль = вечная рассинхронизация с релизами плагина; источник правды об инструментах — живой сервер (`tools/list`, `get_tool_guide`) + пакет `rules/`+`agent/` плагина, обновляемый синхронно с ним.
- **Решение (2026-08-24):** гибрид двух темпов подтверждён. Медленный слой (принципы, гейты, BSL-практики, процесс) — версонируем в модуле; быстрый (имена/параметры инструментов, правила вызова) — всегда из живого контракта (сервер + пакет rules/agent с гейтом версии, Q10).
- **Статус:** закрыт · 2026-08-24

### Q7. Агент-персона 1С в MVP или только слой + setup
- **Решение (2026-08-24):** слой + setup/updater, без отдельной персоны. Правила подмешиваются в существующих агентов BMAD (build/review) через always-on контекст; персона — возможная надстройка после MVP, не ядро.
- **Статус:** закрыт · 2026-08-24

### Q8. Состав правил MVP закрыт или расширять
